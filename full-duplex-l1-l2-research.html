00范围与读法

这份调研覆盖综述 §4.4 的 L1 与 §4.5 的 L2 主体工作，并补充若干综述之后出现、与“双流输入 + 动作控制”直接相关的系统。目标不是把论文摘要堆在一起，而是回答三个工程问题：双轨音频在主干前如何组织、“该不该说/该不该停”由谁在什么粒度上输出、输出之后如何真正改变系统行为。

分级是“控制位置”，不是能力排行榜

L2 的模型不一定比 L1 更会对话，也不一定延迟更低。一个 L1 分类器如果训练充分，可以比一个没有学好静音分布的 L2 模型更可靠。分级真正描述的是：交互控制发生在外部模块、隐藏状态预测头，还是自回归 token 序列里。

“全双工”至少拆成四件事

  • 持续感知：助手发声时仍接收用户音频。
  • 并发建模：同一时间片内同时表示双方音轨。
  • 交互决策：接话、等待、附和、夺话、让话。
  • 并发输出：生成、缓冲、播放与取消互不阻塞。

很多论文只验证其中一两项，不能因为标题写了 full-duplex 就假定四项齐备。

阅读约定 文中标注“论文披露”的是原文可核对的实现；“综述判断”只代表该综述的分类；“综合推断”是根据结构推得的工程结论，尤其涉及运行时播放队列与缓存处理时，许多论文并没有公开完整代码，不能当作已实现事实。

01L0–L3：控制发生在哪一层

综述的关键贡献是把“全双工”从一句能力口号拆成可比较的架构层级，并把决策位置放在中心。下面的表用于快速判断一篇论文究竟属于哪一级，以及它能否直接满足“主干自己决定何时说”的目标。

级别控制放在哪里动作如何产生主要优势主要代价 / 风险代表工作
L0 LLM 外部：VAD、轮次控制器、独立策略模块 外部规则或分类器决定开始/停止，再调用 LLM 或 TTS 模块成熟、容易调试、可替换 误差累积；语义上下文进不了控制决策；回声和“相关打断”难处理 传统级联语音助手
L1 LLM 隐藏状态之后，增加动作预测分支 h_t → Predictor → action，与内容生成分支并行或串行 动作能看到完整上下文；不改主干词表；训练目标清晰 动作与内容生成耦合较弱；分类边界、阈值和状态机仍要额外设计 MinMo、Freeze-Omni
L2 LLM 的 token 生成过程本身 生成状态 token，或直接生成语音/静音 token；动作进入后续上下文 单一自回归目标；动作与内容共享上下文；容易做联合训练 动作与声学生成纠缠；显式标签设计、时间对齐和生成预算更复杂 Moshi、OmniFlatten、SALMONN-omni、Covo-Audio-FD
L3 更深层的表示级整合（综述提出的研究方向） 不是简单的输出 token 或分类头，而是共享表示中的持续交互状态 理论上有机会统一感知、推理与发声 尚无成熟、可复现的统一范式；不能把 L3 当作“更强模型”现成选项 研究假说，而非成熟系统
关键澄清 “有 Linear/Softmax”不等于 L1，“生成 token”也不自动等于 L2。 任何词表输出都需要投影。判断标准是：动作是否作为独立分支、是否脱离主干的下一 token 生成链、以及动作是否真正反馈进后续上下文。另一个常见误判是“文本和语音同时输出”＝全双工；实际上它可能只是半双工的多模态输出。

为什么 L2 内部还要再分型

综述把 L2 统一归为 token 级控制，但在工程上至少有三种很不一样的实现。它们的差别直接决定了数据标注方式和你能否复用 Qwen2.5-Omni 的生成头。

L2 子型动作载体典型模型“不说话”时发生什么标签从哪里来
A. 隐式语音/静音助手音轨的语音 token 或静音 tokenMoshi、SyncLLM、部分 OmniFlatten 阶段继续生成静音或低能量语音 token，模型分布体现时机双轨录音、强制对齐；通常无需独立动作类标
B. 展平同步块固定块内的多流 token 布局 + 特殊静音/说话标记OmniFlatten、BayLing-Duplex输出静音音频 token 与/或 [SILENCE] 类文本标记对齐后的双流会话；块级时序自动派生
C. 显式状态 token<wait>、<shift>、<break> 等离散动作SALMONN-omni、Covo-Audio-FD、DuplexSLA输出等待/思考 token，不启动或暂停内容生成事件边界、意图标注、合成对照数据

对“动作可解释、可审计、可单独加权”的研究目标，C 型最直接；对“尽量少改结构、复用现有语音生成”的工程目标，B 型更平滑；A 型最接近 Moshi 的联合序列建模，但动作语义最难从输出中分离。

02L1：隐藏状态上的动作预测

L1 的共同点是：主干仍然负责理解与内容生成，另有一个轻量预测器读取主干表示并决定交互动作。它不要求把动作写进主干词表，因此适合冻结或半冻结语言模型，但动作与后续 token 生成的闭环需要额外状态机来维持。

MinMo

L1语音输入 / 语音输出 arXiv 2501.06282 ↗
输入
流式语音；SenseVoice-Large 编码后经两层 Transformer + CNN 投影，约 2× 下采样
主干
Qwen2.5-7B-Instruct，LoRA 微调
输出
文本 + 语音：线性投影 → CosyVoice2 Voice Token LM → Token2wav
双工控制
Full Duplex Predictor：1 层 Transformer + Linear-Softmax，约 18M
时间粒度
流式 chunk；论文报告语音到文本约 100ms，但预测器并非固定 100ms 时钟
数据
约 120 万小时 S2T、17 万小时 TTS、1 万小时 S2S；双工约 4,000 小时
  • 核心思想：把“听懂、生成内容”和“决定何时说”拆成两个目标。主干提供语义与声学上下文，预测器只读取 hidden embeddings，输出是否回复/是否继续当前发言等控制决策。
  • 结构：编码器、投影层和 LLM 主体承担理解与文本生成；语音生成由独立声学路径完成；Full Duplex Predictor 随机初始化，在最后的双工对齐阶段单独训练。它不是主干词表中的一个动作 token，也不直接进入自回归内容生成。
  • 动作预测与执行：预测器读取当前主干表示后给出二分类式判断（如 respond / wait、是否在 barge-in 时停止），再由外层运行时决定启动或中断语音路径。论文没有完整披露类别编码、时间窗、阈值和所有状态转移，不能把它的“Speech-to-ControlToken”模块名误读为主干 LM 头直接生成动作 token。
  • 数据构造：约 4,000 小时双工数据由约 3,000 小时真实交互与 1,000 小时模拟交互组成，来源包括 Fisher、AliMeeting 与内部数据；边界、附和等标签以启发式方法生成。它并非一个可公开直接下载的 4k 小时完整双工集。
  • 工程边界：仍依赖外部 VAD/AEC；论文报告理论约 600ms、实际约 800ms 的响应延迟。运行时未完整开源，因此“不回复时是否持续生成静音”不能仅凭论文断言，最合理理解是不启动新的回复生成。
  • 对你的意义：如果坚持“不额外设计动作模块”，MinMo 不是最终形态；但它给出了一个强 baseline：在强 Omni 主干上先接轻量动作头，验证双工数据与标签，再决定是否把动作并入主干 token 流。

状态
三个明确状态：继续接收 / 输入结束且打断 / 输入结束但不打断
决策位置

运行时
model-as-a-server，多实例调度，分离各会话缓存

  • 核心思想：不重训语言能力，冻结 LLM，把语音输入/输出作为可训练的适配层，并在 LLM 表示上增加一个轻量双工状态分类器。这样可以低成本验证“语言模型已经会推理，只缺语音接口和轮次控制”。
  • 动作预测：流式输入按 chunk 推进；每个 chunk 取最后一帧的 LLM hidden state，分类为三种状态。状态 1 表示用户输入结束且需要打断当前助手，状态 2 表示用户输入结束但无须打断；随后由服务层调用相应生成/停止路径。分类交叉熵和语言建模目标联合训练。
  • “模型即服务器”：它不是单个自回归序列天然同时听说，而是用多个模型实例和会话缓存调度来构造并发体验。理解这一点很重要：论文的 L1 分类器只负责决策，真正的并发来自系统层。
  • 数据：大规模内部 ASR 提供语音—文本对齐，TTS 合成提供语音输出监督，MOSS 多轮 QA 提供对话内容；双工阶段再用带打断/轮次边界的数据训练状态分类。
  • 局限：冻结主干意味着交互策略被限制在“在已有表示上分类”，动作无法反过来改变语言模型的内部生成分布；多实例调度也带来显存和会话管理成本。

03L2：把交互动作纳入 token 生成

L2 的共同点是：控制不再只发生在一个独立分支里，而是进入语言模型的生成序列。差别在于动作是“显式的状态 token”，还是“用助手语音/静音 token 隐式表达”。这直接决定了模型输出能否被解释为 wait / respond / backchannel。

  • 动作预测：不是外接分类器，而是在语音 token 词表中加入打断 token。模型正常自回归生成时若产生 IRQ，解码循环立即终止当前话语。这是一个很干净的“动作 token 直接改变控制流”的例子。
  • 数据：LibriTTS 提供干净语音，MUSAN 提供噪声，打断语音由合成或拼接得到；标签主要是“是否发生打断/何时发生”，不是丰富的对话意图标签。
  • 对你的意义：如果你想把“停止发声”做成一个显式 token，LSLM 是最小可行原型；但它没有解决“用户是在附和、纠错还是单纯插话”的语义区分，也没有历史文本条件。

Moshi

L2双音轨 / 语音到语音 arXiv 2410.00037 ↗
主干
Helium 7B
音频
Mimi：12.5Hz（80ms/帧），每路 8 个码本
流
用户音频 8 轨 + 助手音频 8 轨 + 助手文本 1 轨，共 17 条流
建模
Temporal Transformer 处理时间；Depth Transformer 处理同帧码本依赖

无显式动作类标；助手语音/静音分布隐式体现时机
数据
约 700 万小时音频预训练 + Fisher 2,000 小时 + 合成指令/双流数据
  • 思想：把用户和助手都变成连续的离散音频 token 流，用同一个自回归模型预测下一时间帧；助手文本作为“inner monologue”先于语音，帮助语义组织。
  • 双流输入：每一帧的用户 8 个码本、助手 8 个码本和助手文本分别查 embedding，按流/码本区分后在同一隐藏维度组合，送入时间 Transformer。不是把两段长音频首尾拼起来，而是按同一时间片做对齐建模。
  • 动作怎么产生：没有单独的“respond/backchannel”分类头。模型对助手音频码本的下一 token 分布进行采样；如果它生成静音码本，听起来就是没说话。所谓“动作”是生成分布的副产物，不保证内部存在可读的意图变量。
  • 预测与观测的边界：训练时联合预测双方下一帧，学习的是联合动力学；部署时用户轨仍输入真实麦克风观测，不能用模型对用户的预测替代真实输入。否则会把“预测用户会说什么”误当成“听见用户说了什么”。
  • 延迟：论文报告理论约 160ms、实际约 200ms；这是其 80ms 帧、声学缓冲和硬件条件共同决定的，不能与别家的端到端数字直接横比。
  • 对你的意义：Moshi 证明了双音轨 + 单主干的可行性，但它的动作不可解释，而且需要大规模音频预训练。你不必复制它的全部 codec 训练，只需借鉴“同一时间片、双流类型 embedding、因果对齐”三点。

  • 块内顺序：三流阶段按“输入语音 → 输出文本 → 输出语音”排列，文本块与语音块长度不同；文本先于语音，给声学生成提供语义条件。通过静音专用 token 表示当前没有内容输出。
  • 动作预测：模型学习在应当等待时输出静音文本/静音语音 token，在应当回答时输出正常 token。它没有明确的“附和/夺话”类别，动作语义由数据分布和块位置间接决定。
  • 优点：几乎不需要改主干结构，适合从普通 LLM 迁移；课程训练避免了直接从纯文本跳到复杂双流序列的优化困难。
  • 风险：“无需改结构”不等于低成本。序列被多流 token 拉长，推理吞吐下降；固定块内模型看不到尚未到达的用户音频，块边界会限制打断反应；静音 token 的比率过高也会主导损失。

流式 Mamba 语音编码器 + Llama-3-8B-Instruct + 流式 CosyVoice2 合成器
输入

输出

训练
ASR 预训练、QA/多轮、交互数据，最后用 DPO 优化时机
  • 核心思想：不让主干词表装 codec，而是把流式编码器输出、历史助手音频的表示和文本表示按时间块交错送入 LLM，由 LLM 生成文本与状态；声学合成交给流式合成器。
  • 双流如何拼接：在同一时间块内交错环境 embedding（[ENV]）、助手音频 embedding（[SELF]）和回复文本 embedding（[TEXT]），保留流身份，而不是把两条长音轨简单相加。环境轨不是干净用户轨，还包含背景声与自己的回声，这反而更贴近真实部署。
  • 动作预测：在显式策略中，模型可以在每个块生成 <think> 保持等待/填补文本与语音速率差，生成 <shift> 切换听/说状态。动作是普通自回归输出，预测后立即进入下一块的条件上下文；合成器只消费内容 token，不朗读控制 token。
  • 为什么“codec-free”容易误解：它指主干词表不注入音频 codec token，而不是整个系统没有语音 token。合成器内部仍使用 token 做声学生成。理解这一点，才能正确评估它与 Moshi 的差别。
  • 数据：LibriSpeech/GigaSpeech 等 ASR 数据；Alpaca、WebQ、TriviaQA、SQuAD、NQ、VoiceAssistant、UltraChat 等构造 QA；多轮 Trivia/NQ；文本答案由 Llama3-8B-Instruct 生成，语音用 CosyVoice2 合成；另有多轮、语义打断与附和交互数据。
  • DPO：用于偏好对话时机，而不仅是知识正确性；这与“内容相同、时机不同”的偏好对思路一致，适合提升让话与不抢话行为。
  • 对你的意义：最值得借鉴的整体路线：双流 embedding 交错、显式状态 token、周期性同步、合成器与 LLM 解耦。但 80ms 块、4 步缓冲等实现细节不能直接当成 100ms 控制钟。
L2 小结 如果把 L2 理解为“主干生成动作 token”，至少要同时设计三件事：块/帧的时间基、动作词表与状态约束、动作对内容生成与播放的反馈。只加几个 token 而没有时间对齐和反馈，模型仍会退化成普通的半双工对话模型。

  • 思想：用很小的语言模型 + 冻结声学 tokenizer，在双人语音数据上学习“谁在何时以什么方式说话”，并通过提示词控制行为统计。
  • 动作：没有为每个动作单独增加分类器，行为通过语音生成体现；它可以响应“多附和/多打断”的控制，但“次数可控”不等于“每次附和都语义合适”。
  • 对你的意义：适合作为小规模消融：先验证双流数据、行为提示和声学 tokenizer 能否复现基本交互，再把结论迁移到 Qwen Omni。Behavior-SD 的字段与音频形态需要先核对，不能默认任意发布版本都含无损分轨。

05动作预测：三类机制与闭环

比较这些模型时，最容易混淆的是“动作”和“内容”。动作是交互状态（等待、接话、附和、夺话、结束），内容是实际说什么。一个系统可以先生成完整内容再决定何时播，也可以在生成过程中持续决定；两者对数据和延迟的要求完全不同。

5.1 L1：隐藏状态分类

音频流 → 编码器 → LLM 主干 → h_t
                                  ├─→ 内容头 / 文本解码
                                  └─→ 动作预测器 → action_t
                                                   ↓
                                          状态机 / 调度器
                                                   ↓
                                      启动、暂停或取消语音生成

MinMo 与 Freeze-Omni 都属于这一族。它们的共同优点是：可以用一个额外小网络快速试验动作标签；主干不需要学习新的控制词表。共同缺点是：动作预测器不直接改变主干的下一 token 分布，必须依赖外部状态机保证动作与内容一致。

预测后给谁：给运行时控制器，而不是给语音合成器本身。控制器决定是否调用生成路径、是否停止当前 TTS、是否清空缓存。若分类器说“继续听”，通常不应启动新回复；论文没有统一规定是否仍保留一条静音生成流。

5.2 L2 显式状态 token

块输入 = [ENV_t, SELF_{t-1}, 历史文本, 当前状态]
                    ↓
        LLM 自回归生成：CTRL_t → TEXT_t → SPEECH_t
                    ↓
        CTRL_t ∈ {WAIT, RESPOND, BACKCHANNEL, TAKE_FLOOR, YIELD}
                    ↓
        WAIT/YIELD → 不启动或取消播放；其余 → 内容进入合成与播放

SALMONN-omni、Covo-Audio、DuplexSLA 属于这一族。动作 token 是生成序列的一部分，因此下一步生成可以看到它，形成闭环。需要额外设计的是：动作词表的约束（例如说话中不能无意义地产生 RESPOND）、动作 token 的损失权重，以及动作到播放队列的映射。

综合推断 “动作 token 已生成”不等于“声音已经停止”。真正的停止还包括：取消尚未生成的后续 token、丢弃尚未播放的音频、处理设备缓冲区，以及决定历史中是否保留这段未播内容。论文通常只描述模型侧，工程实现必须显式补齐这些环节。

5.3 L2 隐式语音/静音

联合序列：用户语音 token ⊕ 助手语音 token ⊕ 助手文本 token
                         ↓
              按时间帧自回归预测下一帧
                         ↓
      助手帧为静音码本 → 听起来在听；为非静音 → 听起来在说
                         ↓
          外部无法直接读出“wait / backchannel / yield”

Moshi 与 SyncLLM 更接近这种形式。它的优势是：不需要人工定义动作类别，双轨录音天然提供监督；语音和动作在同一个声学生成过程中学习，不会出现“分类器说要停但语音模型还在说”的接口不一致。它的劣势是：动作不可解释，难以为“主动纠错”单独加权，也难做细粒度的动作评估。

06决策、生成、播放：三个时钟不要混在一起

全双工系统的延迟不是一个数字，而是多个时钟串联的结果。很多论文报告“响应延迟 200ms/800ms”，指的是从用户说完到助手首个可听声音，或从用户插话到助手停止，并不等于模型每个控制步都按同样周期运行。

时钟典型值 / 作用设计问题
控制钟80ms、100ms、160ms、800ms 等；决定多久重新判断一次动作越短反应越快，但计算与标签成本越高；控制步不一定等于音频帧
声学帧钟Mimi 80ms / 12.5Hz；CosyVoice 25Hz 等动作每 100ms 一次时，25Hz 音频在 100ms 内是 2.5 个 token，不能简单取整
生成钟文本 token、语音 token、码本的解码速度控制动作产生后，内容生成可能还未完成；需要流式解码与背压
播放钟声卡缓冲、网络抖动缓冲、取消延迟即使模型停止，已进入设备缓冲的音频仍会播放；必须能清空队列

一次打断的完整路径

  1. 感知：用户在助手说话时开始发声，环境流持续送入编码器；不能因为助手正在播报就关闭麦克风。
  2. 判断：L1 预测器或 L2 动作 token 判断这是“继续听”“短附和”还是“需要让话”。判断必须使用当前及历史上下文，不能只看能量。
  3. 控制：若让话，停止旧回复的后续生成，取消未播放的语音，更新对话状态；若只是附和，可以保持当前发言并可能插入短回应。
  4. 恢复：在新用户话语结束后重新判断是否接话；不能让旧的半句话继续污染新的上下文。
工程建议 对话历史建议分成“已生成内容”和“已实际播放内容”两条时间线。训练时 teacher forcing 使用真实播放过的助手音频，而不是模型原本计划但被取消的内容；否则模型会学到用户从未听见的上下文。这个建议来自双工系统的因果结构，不是所有论文都明确实现。

07数据：哪些能直接用，哪些必须自己构造

“有 100ms 推理”不等于“有 100ms 人工动作标签”。真实双轨录音可以自动派生发声/静音边界，却不能自动告诉你“这次重叠是附和还是争抢话权”。因此，数据设计要分成声学对齐、时间事件、语义策略三层。

数据层可直接获得的标签典型来源是否足够训练你的目标
声学与听写音频、转写、说话人、时间戳ASR 语料、TTS 合成语音、公开语音对话不足以学习“何时插话/让话”
时间事件谁在何时发声、重叠、停顿、轮流边界Fisher 等双通道数据；otoSpeech-104h 的分轨与 SRT可训练基础双流节奏，但动作语义仍弱
交互策略等待、接话、附和、夺话、主动纠错、让话人工标注、规则/合成对照、偏好数据必须专门构造；现有公开集无法完整覆盖

7.1 现成数据的正确用法

Fisher 双通道电话语音

约 2,000 小时，天然包含双方同时说话的片段，适合学习轮替、停顿、重叠和声学附和。它不是“AI 助手与用户”的对话，也没有“应该主动纠正错误”的标签；且使用受 LDC 授权约束。([LDC2004S13](https://catalog.ldc.upenn.edu/LDC2004S13))

otoSpeech-full-duplex-turn-104h

约 104.94 小时、420 段双人对话；目录内有 speaker_1_audio.wav、speaker_2_audio.wav、两份 annotation_a.srt 和 metadata.json，因此不只是 Viewer 展示的一个 audio 字段。适合事件级监督；当前为需申请的研究许可，声音克隆与商用需另核授权。

Behavior-SD

官方描述约 108K 对话、2,164 小时，含说话人、起止时间、utterance 类型和行为统计。它可用于研究可控附和/打断，但元数据能恢复事件时间线，不代表任意发布音频都是无损双轨；有重叠时不能按时间裁剪假装拆轨。

通用 ASR / TTS / QA

负责听说能力和知识内容，不负责交互策略。SALMONN-omni 与 OmniFlatten 都先用这类数据建立基础，再叠加双工布局与交互训练；直接把 QA 当双工数据会学到“只要用户停就回答”的伪策略。

7.2 100ms 标签到底怎么来

可以建立一个固定控制网格 t = 0, 100ms, 200ms, ...，每个格子记录：用户是否在发声、助手是否在发声、当前块是否属于话语结束、是否发生重叠、动作类别。前四项可由分轨、VAD 和强制对齐自动派生；最后一项才是需要语义判断的标签。

t(ms)   0    100   200   300   400   500   600
USER    ████████████████████░░░░░░░░░░░░░░░░
ASSIST  ░░░░░░░░████████████████████████████
EVENT           overlap_start              user_end
ACTION  WAIT  BACKCHANNEL  CONTINUE  ...  YIELD

注意：网格上的连续相同标签可以合并为事件区间，不必真的给每一格都人工写一遍。训练时可按事件边界生成标签，并对静音/等待类样本降采样或加权，避免模型只会输出 WAIT。

7.3 最值得自建的四类对照数据

  1. 停顿 vs 结束：同一句话在中间停顿 200–600ms，和真正说完后停顿；前者标 WAIT 或 INCOMPLETE，后者标 RESPOND。这是解决“用户只是换气，助手却抢答”的核心。
  2. 附和 vs 夺话：用户在助手说话时发出“嗯/对/是的”与“等一下，这里不对”。声学上都是重叠，语义动作完全不同，必须成对构造。
  3. 相关纠错 vs 旁人闲聊：用户指出助手事实错误，或背景中有人聊天。两者都可能触发人声，但前者应主动插话，后者应忽略。
  4. 回声与延迟：把助手自己的播放声音以不同延迟和音量混入用户轨，训练模型不要把回声当成用户插话；同时保留真实的双讲场景。
已有工作的证据 MinMo 用 Fisher/AliMeeting/内部数据与启发式标签构造约 4k 小时双工数据；SALMONN-omni 构造多轮与语义打断数据；BayLing-Duplex 用内容相同、时机不同的 DPO 偏好对；DuplexSLA 用双轨 ASR 与时间对齐做 CPT，再做 5 万小时能力后训练。这些都说明策略数据必须单独设计，不是把 ASR 数据换个采样率就能得到。

09面向 Qwen2.5-Omni 的改造方案

目标不是“把 Qwen Omni 改得和 Moshi 一模一样”，而是复用它已有的语音理解、文本推理和语音合成能力，补上“持续双轨感知 + 主干动作 token + 可取消播放”三块。下面方案是结合前述论文的综合设计，不是 Qwen2.5-Omni 原生支持的功能。

9.1 推荐的第一版结构

用户麦克风 ──► 因果音频编码器 ──► [USER_t] ─┐
                                             ├─► 交错/拼接层 ─► Omni 主干
助手播放参考 ─► 因果音频编码器 ──► [SELF_t] ─┘        │
                                                     ├─► 动作 token（WAIT/RESPOND/...）
历史文本 / 角色 ─────────────────────────────────────┘   └─► 文本 token ─► Talker ─► 播放
  • 保留主干：先不动 Thinker 的语义能力，把新增预算放在输入适配、动作词表和双流布局上。这样可以把“语言能力退化”和“交互策略没学会”两个问题分开诊断。
  • 双流输入：用户与环境音轨、助手实际播放音轨分别编码，使用流类型 embedding 区分，再按时间块交错送入主干。推荐先做序列交错，不要未经训练就把两路 embedding 逐元素相加；相加会丢失流身份，也更难排查回声问题。
  • 历史文本：放在序列前部或作为每个块的前缀条件，明确标记“说的是谁、何时说、是否实际播放”。不要让历史文本和当前音频竞争同一个位置编码。
  • 动作 token：在主干词表中加入控制 token，动作生成后继续进入上下文；控制 token 不送 Talker 朗读。第一版可以先只做 WAIT / RESPOND / YIELD，稳定后再加 BACKCHANNEL / TAKE_FLOOR。

9.2 动作词表：建议与状态约束

Token（建议命名）含义允许的当前状态执行语义
<wait>继续听，用户可能没说完助手静默或正在短附和不启动新的正式回复；保持环境流输入
<respond>接过已结束的轮次用户话语结束，助手未在长发言启动内容生成与语音合成
<backchannel>短附和，不夺话助手正在说，用户发出短反馈可插入极短语音，不改变主发言计划
<take_floor>主动插话/纠错助手正在说，用户内容与当前话题相关且需纠正停止或压低当前语音，转入新回复
<continue>继续当前发言助手正在说，用户未夺话保持生成与播放

9.3 100ms 设计要注意什么

100ms 控制周期是合理的工程选择，但不能直接假设所有音频 tokenizer 都按 100ms 对齐。以 25Hz 语音 token 为例，100ms 只有 2.5 个 token；以 80ms 帧为例，100ms 不是整数帧。可选方案有三类：

  1. 控制钟 100ms，声学钟独立：每 100ms 做一次动作判断，声学 token 按自身帧率累计生成；动作只在块边界生效。实现简单，但动作与音频帧要维护映射表。
  2. 统一到 80ms 或 160ms：采用与编码器/声学模型原生帧率一致的块长，减少取整误差。Covo/DuplexSLA 用 160ms，Moshi 用 80ms，都是这个思路。
  3. 事件驱动：控制判断按 100ms 运行，但真正的停止由“动作 token + 声学事件”共同触发，不必等到下一个完整音频块。复杂度更高，需要严格处理因果性。
不要混淆“控制粒度”与“可听延迟” 100ms 推理一次，不代表用户 100ms 内一定能听到回应。编码器前视、主干计算、声学解码、网络与播放缓冲都会叠加。建议分别记录：动作决策延迟、首 token 延迟、首包音频延迟、可听首字延迟、打断后静音延迟。

Stage A：格式适配让主干理解双流块、历史文本和静音普通对话 + 合成双流 + 自动派生的发声/静音标签先冻结大部分声学模块；动作只用少量类别，重点避免语言能力退化
Stage B：基础双工学会等待、接话、被打断后停止Fisher/otoSpeech 等双轨数据 + 合成的插话与停顿联合动作 CE + 文本/语音生成损失；对 WAIT 降采样，给 YIELD 更高权重
Stage C：语义交互附和、主动纠错、区分旁人语音人工标注或高质量合成对照数据；噪声/回声增强动作标签必须结合上下文；单看重叠率会奖励错误抢话
Stage D：偏好优化改善时机与自然度内容相同、动作/时机不同的偏好对可参考 BayLing 的 DPO；不要让偏好模型只奖励“更长的回答”

训练时建议采用 teacher forcing 的真实历史：只把用户实际听见的助手音频放入上下文，未播出的内容不作为历史。否则模型会高估自己已经说过的内容，导致重复或逻辑跳步。

9.5 评测不要只看回答质量

交互指标

  • 误抢话率：用户尚未说完就接话的比例。
  • 漏接话率：用户明确结束后仍不回应。
  • 附和精确率/召回率：该附和与不该附和是否分开。
  • 打断后残留播放时长：模型决定停止后还有多少声音。
  • 相关打断正确率与不必要打断率。

声学与系统指标

  • 首字延迟、打断响应延迟、端到端响应延迟。
  • 回声下的误触发率、双讲时的识别质量。
  • 语音自然度、语义一致性、长对话记忆保持。
  • 不同块长与动作词表的消融结果。
当前研究缺口 2026 年的 Full-Duplex Speech Models Take the Floor When Asked, Not When Needed 报告了对五类模型的分析：被点名或静音更容易触发发言，而错误事实或危险内容并不稳定触发主动打断。这直接说明“能被打断”与“会在语义上必要时主动打断”是两种能力，你的纠错目标必须单独建数据和评测。
