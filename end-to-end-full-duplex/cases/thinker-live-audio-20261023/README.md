# Thinker 生成期间增量接收音频的验证

## 目标与边界

验证同一个 Thinker KV 缓存能否交替接收后到音频 embedding 与模型生成的文本 token，而不是保存音频表示后在句尾重新调用 `generate()`。

保留 95 上现有 `Qwen2.5-Omni-3B` 的权重与原生音频编码器。单卡 A800、BF16、eager attention，不训练、不改公共依赖、不全量解包数据。关闭 Talker，所以这是输入音频/输出文本的增量接口实验，不是语音播放、用户打断或双轨全双工演示。

## 调度方式

1. 接收首 1 秒音频，按原生 processor 的处理方式编码，使用正常 system/user/assistant 头部开始生成。对照原生 `forward()`，检查手动 embedding 注入与显式位置编号的初始结果。
2. 每到达新的 100 ms，重算从话语开始到当前的音频前缀，只取未提交的新位置，已提交表示冻结。先按原始采样率截断，再重采样与提取 Mel，不使用未来真实波形。
3. 将新增音频表示作为当前序列的后续输入传入 `thinker.forward(inputs_embeds=..., past_key_values=...)`，然后生成、写入一个文本 token。保持相同缓存对象，检查实际缓存长度与累计写入长度严格一致。
4. 采用显式单调递增的三轴位置编号与全因果 attention。纯音频初始输入通过原生路径对照，但不宣称这是未来双轨训练的最终时间位置设计。
5. 到已知句尾后最多继续生成 64 个文本 token，以便检查剩余输出。这是 oracle endpoint；尚未实现终点或行为预测。

插入点位于 assistant continuation 内，原生权重没有针对这种序列布局完成过本项目的适配训练。

## 对照

- `natural_live`：每 100 ms 插入新音频，保留自然 EOS。若模型已结束，后续仍可写入音频，但不将其统计为“持续生成”。
- `natural_initial_only`：只提供首秒音频，按相同文本输出预算解码，保留自然 EOS。
- `forced_live`：持续插入真实音频，到句尾前屏蔽 EOS，只用于诊断接口持续运行，不代表模型自然具有持续输出能力。
- `forced_silence`：首秒与真实组完全相同，后续改为独立编码的静音前缀的新表示。音频位置、音频包数量与文本输出预算保持一致。自由输出文本历史可能分叉，因此另设严格配对的因果对照。
- 因果配对：真实与静音两条缓存先使用相同首秒和同一个首文本 token；每次插入等长音频后比较 logits，再向两条缓存都写入真实组选择的同一个文本 token。这样在每次比较前，文本历史和序列位置完全一致。
- 缓存重放：将每条增量序列实际提交过的 embedding 原样拼接，以同样位置与因果掩码做一次无缓存完整 forward，对比最终 logits。此对照不是与整句离线音频编码比较，而是验证缓存调度本身。

同时比较两种新音频包序列化方式：原生 audio-bos/eos 包裹，以及不添加包边界、直接插入音频 embedding。不能从单一序列化方式的失败推断所有流式结构不可行。

普通对照组按来源时间戳离线重放，预先计算每个已到达前缀的音频包以保证各组 payload 一致；它们不是麦克风实时吞吐测试。另设 wall-clock-paced 模式：不预计算音频包，严格在 100 ms 到达时刻后才提取当前前缀、写缓存并解码，记录真实完成时间与积压。

## 接口与质量结果

### 带包边界：8 条语音

`run-01` 使用原生 audio-bos/eos 包裹每个新增音频包，8 条语音、135 个参考词：

| 策略 | 词编辑数 | micro-WER |
| --- | ---: | ---: |
| 整句离线原生转写 | 11 | 8.15% |
| 自然 EOS，生成中持续插入音频 | 147 | 108.89% |
| 自然 EOS，仅首秒音频 | 122 | 90.37% |
| 屏蔽 EOS，持续插入音频 | 146 | 108.15% |
| 屏蔽 EOS，后续改为静音 | 328 | 242.96% |

WER 允许超过 100%，例如生成了大量标注中不存在的词。这里对自然/强制策略都使用相同整句参考词，只提供首秒的对照预期不能完整转写，不能将其 WER 解释为模型识别首秒的准确率。

工程检查：

- 8 条首秒输入的自定义 embedding/显式位置路径与原生 forward 的初始 logits 完全相同，最大差值均为 0。
- 8 条因果配对在后到音频插入前，logits 最大差值均为 0；后续 442 次真实/静音配对中，50 次改变了 greedy 下一 token；平均绝对 logit 差约 1.6981。文本历史、音频位置和包数量相同，支持“后到音频确实进入主干并影响预测”，不代表被正确理解。
- 4 组共 32 条缓存序列全部满足缓存对象持续复用、长度增长正确。实际序列完整重放的最终 argmax 均与缓存结果一致。
- BF16 重放 logits 并非逐位一致：32 次的最大绝对差最高为 0.84375，平均绝对差再平均约 0.07232。脚本以末位 argmax 一致且最大差不超过 1 为运行诊断门槛；这是本实验的检查阈值，不是严格数学等价证明，也未单独进行 FP32 等价验证。
- 实际有 385 次在写入后到音频后继续生成文本的事件；不含模型已输出 EOS 后仅继续写入音频的事件。

接口跑通并没有转化为合理输出。例如首条话语会在前期混入 `transcript`，第二条出现连续 `WithWithWith...`。第一条在音频只到 1.3 秒时就自然结束，其他样本也大量出现重复符号或词语。因此这套未经训练的序列布局不能作为可用的在线转写或对话方案。

### 不带包边界：同一批中的前 3 条

`run-02-bare` 不再插入 audio-bos/eos，只插入新增音频 embedding。使用确定的同 3 条样本，63 个参考词，未因结果重选样本。

| 策略 | 带边界，前 3 条 | 不带边界，前 3 条 |
| --- | ---: | ---: |
| 整句离线原生转写 | 6.35% | 6.35% |
| 自然 EOS，持续插入音频 | 98.41% | 96.83% |
| 屏蔽 EOS，持续插入音频 | 96.83% | 92.06% |

不带边界的自然生成全部在第一个后到音频包，即来源时间 1.1 秒，输出 EOS，文本分别仅为 `I`、`hi`、`it`。屏蔽 EOS 后可继续写缓存和输出，但质量仍不可用：空行、重复标点和偏离原文的续写很多。不能用自然组较低运行耗时声称持续生成满足预算，因为它们已停止输出。

不带边界的严格配对共有 201 次后到更新，103 次改变 greedy 下一 token，平均绝对 logit 差约 2.2936。新音频有影响，但没有因此形成可靠的连续理解/生成能力。

### 真实时钟的到达重放

在同 3 条语音上，不预计算音频包，到来源时刻后才重算当前前缀、写入音频缓存并生成。初始 1 秒已到达后开始计时，后续按 100 ms 到达；句尾可有不足 100 ms 的最后一批。输入来自已有录音而非麦克风，不包含网络、Talker 或播放。

| 不带边界策略 | 更新步数 | 单步平均 | P95 | 超过 100 ms 的步数 |
| --- | ---: | ---: | ---: | ---: |
| 自然 EOS | 201 | 105.35 ms | 121.08 ms | 151 |
| 到句尾前屏蔽 EOS | 201 | 129.69 ms | 144.03 ms | 201 |

自然组仍全部在来源 1.1 秒时停止输出，之后的耗时主要是接收音频，不可解释为持续文本生成预算。其文本与非 paced 的自然组逐字一致。

强制组的单步开销分解均值约为：前缀重采样/Mel/编码 71.63 ms，音频写入 Thinker 29.34 ms，文本 token 写入 Thinker 27.78 ms，另有调度与 token 选择开销。该实现每步串行运行音频与文本两个 forward，没有融合调用或异步重叠优化。

强制组 3 条样本的最终音频批次完成时间相对到达时间分别落后约 1.825 秒、1.274 秒、3.398 秒；最大值对应 11.622 秒话语。这是音频批次处理积压，不是首音频延迟，也未计入句尾额外 drain 的输出耗时。

3 条强制输出的全文与非 paced 的 `forced_live` 逐字一致，WER 仍为 92.06%。共 200 个步骤同时有新增音频位置与文本生成；剩余 1 个句尾到达步骤没有新增音频 token。所有 paced 组的缓存长度检查通过，完整重放的最终 argmax 相同，BF16 数值差异与前述对照一致。

因此，本次真实时钟实现**没有满足 100 ms 持续吞吐**。此前仅测音频编码器的耗时不包含这些 Thinker forward，不能当作完整增量生成预算。

### 结论的适用范围

本次验证将原先两个阶段区分开了：上次“冻结在线表示，等句尾拼完后转写”的 9.63% WER，只支持音频表示保留内容；本次“边插入音频边生成”会引入交错序列分布、自然 EOS 与调度问题，不能沿用前一个数字宣称在线生成质量已通过。

支持继续复用原生 encoder 和 Thinker 权重；但应先确定音频、文本、行为 token 的交错训练序列，再用同样的在线冻结策略适配训练。当前固定每 100 ms 输出 1 个文本 token 的调度只是探针，不是已选定的最佳训练或推理方案。本实验不证明所有未经训练的提示/序列化策略都不可能成功，也没有证明适配训练后必然达到目标。

优先后续工作应分开：一条处理交错序列的训练与 `<silent>`/`<speak>` 等行为状态，避免把文本 EOS 当作整个会话结束；另一条优化预处理、有限前缀重算与每步 forward 调度。任何融合调用、注意力实现切换或并行化都需要重新做缓存和计时对照，不能预先宣称会满足预算。

## 复现

在具有现有模型依赖的服务器中，使用一个尚不存在的输出目录：

```bash
CUDA_VISIBLE_DEVICES=5 HF_HUB_OFFLINE=1 TRANSFORMERS_OFFLINE=1 \
TOKENIZERS_PARALLELISM=false OMP_NUM_THREADS=4 \
python script/probe_thinker_live_audio.py \
  --model-dir /path/to/Qwen2.5-Omni-3B \
  --dataset-dir /path/to/behavior-sd \
  --output-dir /path/to/new-run --sample-count 8
```

`--packet-style bare` 切换为不包裹边界的音频输入；`--paced` 运行真实时钟的到达重放；只有显式指定 `--paced-suppress-eos` 才在该模式下强制持续输出。测试脚本依赖同目录的 `probe_omni_streaming_encoder.py`。

测试使用原先同一确定性选择规则：从 `test/0000.tar` 顺序取不同对话的首条合格话语，3 至 12 秒、无主话语重叠/附和/打断、非纯非语言事件。不按输出重选样本。
